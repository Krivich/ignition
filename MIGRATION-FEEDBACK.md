# Обратная связь по миграции demo.html на Ignition

## Что делали

Взяли демонстрационный файл [`demo.html`](./demo.html) — форму "Предложить кандидата для трудоустройства" (External Mobility) — и реализовали её как полноценную страницу на Ignition v2:

- **Данные:** [`input/data/extmob/recommend.json`](./input/data/extmob/recommend.json)  
  reference-справочники (индустрии, города, полы, подсказки навыков) + prefilled-кандидат + список навыков + UI-состояние.
- **Layout-шаблон:** [`input/templates/extmob.hbs`](./input/templates/extmob.hbs)  
  разметка и стили из demo.html, автобиндинги полей, селекты с `placeholder`-проекцией, авто-блок навыков.
- **Partial-блок навыков:** [`input/templates/extmob/skills.hbs`](./input/templates/extmob/skills.hbs)  
  строки навыков с кнопкой удаления и звёздным рейтингом.
- **Внешний контроллер:** [`input/controllers/extmob.js`](./input/controllers/extmob.js)  
  добавление/удаление навыков, валидация формы, звёздный рейтинг, тосты, очистка формы, заглушки кнопок.
- **Результат сборки:** [`output/public/extmob/recommend.html`](./output/public/extmob/recommend.html)

Также обновили [`tests/requirements/H-reliability.test.js`](./tests/requirements/H-reliability.test.js): старый `demo` layout был удалён из проекта до начала работ, поэтому тесты, которые ожидали `demo/app.html`, переключены на новую страницу `extmob/recommend.html`.

## Результат

- `npm run build` — успешно.
- Ручной jsdom-smoke — биндинги, реактивный блок навыков, валидация, рейтинг, clear работают.
- `npm run test` — **337 passed / 42 test files**.

## Критика фреймворка и документации

> Примечание: работа велась как миграция существующего HTML. Часть трения связана именно с этим (нужно было сохранить чужую разметку, ID, классы и предзаполненные значения). Но ниже перечислены пробелы, которые проявляются и при разработке с нуля.

### 1. Нет явного объяснения жизненного цикла страницы

AGENTS.md хорошо объясняет архитектуру Model/View/External Controller, но не даёт пошаговую картину:

```
шаблон + данные → SSR HTML + __IGNITION_INITIAL_DATA__ + __IGNITION_TEMPLATES__
      ↓
браузер грузит runtime
      ↓
runtime строит реактивный state
      ↓
replay контроллеров
      ↓
блоки/биндинги живут
```

Без этой картины непонятно, когда можно обращаться к `window.ignition`, что уже вставлено в HTML, а что нужно доделать в контроллере.

### 2. API контроллера не задокументировано

В [`REACTIVITY.md`](./REACTIVITY.md) раньше встречался `window.__IGNITION_PAGE_CONFIG__`, а реально работающий паттерн — `window.ignition.controller(function(state, api) {...})` (см. [`input/controllers/catalog.js`](./input/controllers/catalog.js)).

✅ Разрешено: легаси-хук `__IGNITION_PAGE_CONFIG__` удалён из движка и всех фикстур; всюду только `window.ignition.controller`.

Нигде нет референса:
- как зарегистрировать контроллер;
- когда он запускается (после гидратации);
- что содержится в `api` (`registerHelper`, `blockOptions`, `afterHydrate`);
- что `state` — это Proxy, а не plain object.

Пришлось смотреть исходники рантайма и существующий контроллер.

### 3. «Автомагия» движка не описана как поведение

Даже при разработке с нуля важно понимать, что делает движок сам:

- `value="{{path}}"` → рендерит `value` **и** инжектит `data-ignition-binding="path"`;
- `{{> foo/bar data}}` → оборачивает в `<div data-ignition-block="foo/bar" data-ignition-data="...">`;
- `input/controllers/{layout}.js` → рендерер сам вставляет `<script src="/assets/controllers/{layout}.js">`;
- `__IGNITION_INITIAL_DATA__`, `__IGNITION_TEMPLATES__`, preload-ссылка на `/data/...json` вставляются автоматически.

Это неочевидно, пока не посмотришь сгенерированный HTML или исходники рендерера. Документация должна явно перечислять: «движок автоматически делает X, Y, Z; вы пишете A, B, C».

### 4. Непонятны три режима загрузки данных

В проекте одновременно существуют:

- `__IGNITION_INITIAL_DATA__` — полный датасет для интерактивных страниц;
- `__IGNITION_MANIFEST__` — компактный манифест для block-only страниц;
- `<link rel="preload" href="/data/...json">` — параллельная загрузка полного датасета.

Документация упоминает их, но не объясняет, когда движок выбирает тот или иной способ. Нужна таблица: «если в шаблоне есть биндинги/actions → полный initialData; если только блоки → manifest + loadDataset; preload всегда для интерактивных страниц».

### 5. Ловушка с булевыми атрибутами

Для чекбокса `checked="{{path}}"` SSR рендерит `checked="false"`, но браузер считает присутствие атрибута за `true`. Пришлось делать вручную:

```hbs
<input data-ignition-binding="candidate.consent" {{#if candidate.consent}}checked{{/if}}>
```

То же самое касается `selected`, `disabled`, `readonly`. Нужен явный раздел в документации с правилами для булевых атрибутов (или поддержка на уровне компилятора).

### 6. Именование авто-блоков неочевидно

`{{> extmob/skills skills}}` создаёт блок с именем `extmob/skills`. Это важно для `api.blockOptions.renderers['...']` и `sourceDeps`. Хотелось бы явной строки в доке: «имя блока = путь partial'а».

### 7. Авто-биндинг через regex хрупкий

Компилятор делает post-processing готового HTML регулярками и вставляет `data-ignition-binding`. Это работает для стандартных случаев, но разработчик не видит `data-ignition-binding` в исходном шаблоне. Если разметка пишется с необычными кавычками или переносами, есть риск промаха. Лучше либо задокументировать точные правила, либо сделать инжекцию на уровне Handlebars-парсера.

### 8. Проект находится в переходном состоянии

Старый `demo` layout (`input/templates/demo.hbs`, `input/data/demo/app.json`) удалён, но тесты и README ещё ссылаются на него. Из-за этого `npm run test` падал до правки `H-reliability.test.js`. Это создаёт путаницу: непонятно, какой сейчас канонический способ делать страницы.

## Что понравилось

- **SSR + гидратация работают чисто**: HTML без JS уже содержит контент и форму.
- **Авто-блоки из partial'ей элегантны**: `{{> extmob/skills skills}}` сразу даёт реактивный регион.
- **Один источник хелперов** ([`engine/core/helpers.js`](./engine/core/helpers.js)) для сервера и клиента — последовательно.
- **Широкий тестовый набор** — 337 тестов дают уверенность при изменениях.

## Рекомендации по документации (универсальные, не только для миграции)

1. **Страница «Жизненный цикл страницы»** — от Handlebars до гидратации.
2. **Референс `window.ignition.controller`** — сигнатура, `api`, порядок вызова.
3. **Справочник «Что делает движок автоматически»** — авто-блоки, авто-биндинги, авто-подключение контроллера, авто-инжект данных/шаблонов.
4. **Справочник режимов данных** — `initialData` / `manifest` / preload, когда какой.
5. **Каталог биндингов и проекций** — все input-типы и булевы атрибуты с примерами.
6. **Убрать/обновить упоминания старого demo** в README, тестах и примерах.

Фреймворк держит сильную идею: JSON + Handlebars, SSR с гидратацией, внешний контроллер. Сейчас документация похожа на список фич, а не на объяснение модели. Исправить это — главное, что стоит вынести из этого опыта.
